Les Tests Unitaires JavaScript / React

Un guide simple pour tester et sécuriser votre code.

Objectif : comprendre quoi tester, pourquoi, et comment.

Utilisez Suivant pour avancer.

1) Définition

Un test unitaire vérifie qu'une petite unité de code fonctionne correctement de manière isolée.

Une unité peut être :

  • Une fonction (sum, formatDate, etc.)
  • Un hook (useFetch, useCounter)
  • Un composant React simple (Hello, Button, etc.)
L'idée : prouver que cette unité fait exactement ce qu'on attend.

2) Pourquoi des tests unitaires ?

a) Détecter les bugs tôt

Tu trouves les erreurs pendant le développement, pas en production.

b) Éviter les régressions

Un test qui échoue te signale qu'un comportement ancien a été cassé.

c) Gagner du temps

Au lieu de vérifier à la main, tu lances npm test.

d) Refactor sereinement

Si les tests passent, le comportement reste correct.

3) Test manuel vs Test unitaire

Test manuel (npm start)

  • Tu ouvres la page
  • Tu cliques
  • Tu valides visuellement

Lent, incomplet, non reproductible.

Test unitaire (npm test)

  • Automatique
  • Mêmes scénarios à chaque run
  • Résultat immédiat

Rapide, fiable, reproductible.

4) Structure d'un test (AAA)

1. Arrange

Préparer le contexte : données, objets, mocks.

2. Act

Exécuter l’action : appeler la fonction / interagir.

3. Assert

Vérifier le résultat attendu.

Base de la majorité des tests unitaires.

5) Exemple : Tester une fonction

Code à tester : sum.js

export function sum(a, b) { return a + b; }

Test : sum.test.js

import { sum } from "./sum"; test("sum adds two numbers", () => { expect(sum(2, 3)).toBe(5); });
Quand j'appelle sum(2,3), je dois obtenir 5.

Image 1 : Tests multiples

Plusieurs tests unitaires : cas positifs, négatifs, etc.
Chaque test("...") vérifie un comportement précis.

6) Exemple React : Composant

Composant : Hello.jsx

export function Hello({ name }) { return <h1>Hello {name}</h1>; }

Test : Hello.test.jsx

import { render, screen } from "@testing-library/react"; import { Hello } from "./Hello"; test("shows the name", () => { render(<Hello name="Badr" />); expect(screen.getByText("Hello Badr")) .toBeInTheDocument(); });

Interprétation du test React

  • render(...) → affiche le composant
  • getByText("Hello Badr") → cherche le texte
  • toBeInTheDocument() → le texte doit exister
Résultat dans le terminal : PASS.

7) Tester App ne teste pas tout

Si tu fais juste :

render(<App />);

Tu testes seulement : App ne crash pas.

Pour tester ce qu'il y a dedans :

Il faut écrire des assertions (expect(...)) sur ce que l'utilisateur doit voir ou faire.

Petits composants → tests unitaires séparés.
App → tests légers (intégration).

Image 3 : Fichiers de test

Jest détecte automatiquement les fichiers *.test.js(x).
Ils sont trouvés et exécutés automatiquement.

8) Où apparaissent les erreurs ?

Quand tu lances npm test :

  • Les résultats apparaissent dans le terminal / VS Code
  • Tu vois :
    • Le nom du test en échec
    • Le fichier + la ligne
    • Attendu vs obtenu

Si le code casse avant d'entrer dans un test :

“Test suite failed to run” et 0 tests exécutés.

9) Règles d'or (Best Practices)

1 test = 1 comportement

Un test doit viser une seule attente claire.

Nommer clairement

Ex : “affiche un message si champ vide”.

Tester l'expérience utilisateur

Ce que l'utilisateur voit et fait.

Préférer plusieurs tests simples

Plutôt qu’un gros test compliqué.

Conclusion

Les tests unitaires sont :

✅ Un filet de sécurité automatique

✅ Rapides et fiables

✅ Évitent les régressions

✅ Indispensables quand le projet grandit
